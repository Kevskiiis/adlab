Identity and Access

This page covers the lab's user accounts, security groups, and how group membership maps to resource access.

Summary

  • Ten fictional accounts across four departments.
  • Access is organized through security group membership instead of individual user permissions.
  • Security groups follow the <Type>_<Resource>_<Role> naming pattern. SMB folder groups use G_<Resource>_Read / G_<Resource>_Modify.
  • Security group membership and effective access validation are in progress.

Group Structure and Naming Pattern

Format<Type>_<Resource>_<Role>
TypeG (Global), DL (Domain Local), or U (Universal)
ResourceThe asset being protected (folder, application, service, etc.)
RoleThe access level or responsibility (Read, Modify, Admin, etc.)

Implementation Details

Flexible structure

The <Type>_<Resource>_<Role> naming pattern supports security groups across all resources in the environment.

Group-based access

Security groups control access to resources instead of permissions being applied directly to user objects.

Current deployment

Global security groups with Read and Modify roles have been created for DoomVault resource access.

Validation

Security group membership completion and effective access validation are still in progress.

Design Decisions

Groups instead of individual permissions

Using groups separates user identity from resource permissions.

Separate read and modify groups

Access is based on assigned responsibilities, supporting least privilege.

Resource-and-access naming

The group name tells an administrator what it controls and at what level.

Production Considerations

This lab is not a production design. Outside a lab, these are the changes I would make.

What I would change

  • Review: Define a documented process for identity lifecycle administration.
  • Review: Define a documented process for reviewing group membership.
  • Review: Establish a regular access review process.

Not yet addressed in the lab

  • Password and lockout policy.
  • Auditing and logging.
